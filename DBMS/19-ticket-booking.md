# Concurrent Ticket Booking Problem (একই সময়ে একাধিক ব্যক্তির টিকিট বুকিং)

সিস্টেম ডিজাইন (LLD) এবং ডাটাবেস ইন্টারভিউয়ের জন্য এটি একটি ক্লাসিক প্রশ্ন। "যদি একই সময়ে দুজন ইউজার একই মুভি বা ট্রেনের একই সিট বুক করার জন্য ক্লিক করে, তখন সিস্টেমে কী ঘটবে এবং ডাটাবেস লেভেলে এটি কীভাবে সমাধান করা যায়?"

---

## ১. The Problem Statement (সমস্যাটি কী?)

এটি মূলত একটি **Race Condition** বা ডাটাবেসের ভাষায় **"Lost Update Problem"**। 
যখন একাধিক কনকারেন্ট ট্রানজেকশন (Concurrent Transactions) একই ডাটা রিড (Read) করে এবং তার উপর ভিত্তি করে ডাটা আপডেট (Update) করার চেষ্টা করে, তখন এক ইউজারের আপডেট অন্য ইউজারের আপডেট দিয়ে ওভাররাইট হয়ে যেতে পারে। 

ফলে দেখা যায়, একটি সিটের বিপরীতে ২ জনের নামে বুকিং কনফার্ম হয়ে গেছে! একে **Double Booking** বলা হয়।

---

## ২. Table Design & Use Case (টেবিল ডিজাইন)

ধরা যাক, আমাদের `Seats` নামে একটি ডাটাবেস টেবিল আছে। 

| seat_id (PK) | movie_id | is_booked | booked_by_user | version |
| :--- | :--- | :--- | :--- | :--- |
| 101 | 55 | FALSE | NULL | 1 |
| 102 | 55 | FALSE | NULL | 1 |

*   `seat_id`: সিটের ইউনিক আইডি।
*   `is_booked`: সিটটি বুক করা হয়েছে কিনা (TRUE/FALSE)।
*   `version`: এটি অপটিমিস্টিক লকিং এর জন্য ব্যবহার করা হবে (পরে ব্যাখ্যা করা হয়েছে)।

---

## ৩. সমস্যাটি কীভাবে ঘটে? (Without any lock)

ধরা যাক, ইউজার A এবং ইউজার B দুজনেই `seat_id = 101` বুক করতে চায়। 

**টাইমলাইন (Time: T1, T2, T3, T4):**
1.  **T1:** User A ডাটাবেস থেকে চেক করলো সিট ফাঁকা আছে কিনা।
    `SELECT is_booked FROM Seats WHERE seat_id = 101;` (রেজাল্ট: FALSE)
2.  **T2:** ঠিক একই মিলিসেকেন্ডে User B ও ডাটাবেস থেকে চেক করলো।
    `SELECT is_booked FROM Seats WHERE seat_id = 101;` (রেজাল্ট: FALSE)
3.  **T3:** User A দেখলো সিট ফাঁকা, তাই সে সিটটি নিজের নামে আপডেট করে নিলো।
    `UPDATE Seats SET is_booked = TRUE, booked_by_user = 'User A' WHERE seat_id = 101;`
4.  **T4:** User B ও তো আগেই দেখে রেখেছিল সিট ফাঁকা। তাই সেও সিটটি আপডেট করলো।
    `UPDATE Seats SET is_booked = TRUE, booked_by_user = 'User B' WHERE seat_id = 101;`

**ফলাফল:** User B এর আপডেটটি User A এর আপডেটকে ওভাররাইট করে ফেললো। User A এর বুকিংটি হারিয়ে গেল (Lost Update), কিন্তু সিস্টেম দুজনকে সফল মেসেজ দেখালো।

---

## ৪. সমাধানসমূহ (Database Level Solutions)

এই ডাবল বুকিং আটকানোর জন্য মূলত ৩ ধরণের সমাধান আছে। 

### সমাধান ১: Pessimistic Locking (পেসিমেস্টিক লকিং)

পেসিমেস্টিক লকিং মানে হলো "আমি নেগেটিভ চিন্তা করছি, আমি জানি অন্য কেউ এই ডাটা মডিফাই করার চেষ্টা করবেই।" তাই আপনি যখনই সিটটি রিড করবেন, তখনই সেটিতে একটি এক্সক্লুসিভ লক (Exclusive Lock) লাগিয়ে দেবেন। 

লক লাগানোর ফলে, আপনার বুকিং শেষ না হওয়া পর্যন্ত অন্য কেউ ওই সিটটি রিড বা রাইট করতে পারবে না।

**SQL Query Example:**
```sql
BEGIN TRANSACTION; -- ট্রানজেকশন শুরু

-- Step 1: সিটটি রিড করার সাথে সাথেই লক করে ফেলুন (FOR UPDATE ব্যবহার করে)
SELECT is_booked 
FROM Seats 
WHERE seat_id = 101 
FOR UPDATE;

-- (যদি is_booked = FALSE হয়, তবে নিচের কোড রান করবে)

-- Step 2: সিট বুক করুন
UPDATE Seats 
SET is_booked = TRUE, booked_by_user = 'User A' 
WHERE seat_id = 101;

COMMIT; -- ট্রানজেকশন শেষ এবং লক রিলিজ করা হলো
```

**কীভাবে কাজ করে?**
*   `FOR UPDATE` অংশটি ডাটাবেসকে নির্দেশ দেয় যে, আমি এই রো (Row) টি আপডেট করার জন্য রিড করছি। 
*   ইউজার A যখন `FOR UPDATE` কল করে, ওই রো-টি লক হয়ে যায়। 
*   ইউজার B যদি একই সময়ে `SELECT ... FOR UPDATE` কল করে, তবে ডাটাবেস তাকে ডাটা দেবে না। ইউজার B এর রিকোয়েস্টটি ওয়েটিং-এ (Waiting/Blocked) চলে যাবে।
*   ইউজার A এর কাজ শেষে `COMMIT` হলে লক খুলে যাবে, তখন ইউজার B ডাটা রিড করবে এবং দেখবে `is_booked = TRUE` হয়ে গেছে। ফলে ইউজার B আর আপডেট করবে না।

**সুবিধা:** ডাবল বুকিং ১০০% ঠেকানো যায়।
**অসুবিধা:** এটি স্লো। ইউজাররা লাইনে আটকে থাকে (Blocked), তাই হাই-ট্রাফিক সিস্টেমে পারফরম্যান্স খারাপ হতে পারে।

### সমাধান ২: Optimistic Locking (অপটিমিস্টিক লকিং)

অপটিমিস্টিক লকিং মানে হলো "আমি পজিটিভ চিন্তা করছি, সাধারণত কেউ আমার ডাটা মডিফাই করতে আসবে না। যদি আসে, তখন আমি রিজেক্ট করে দেব।" 
এখানে আমরা ডাটাবেসকে লক করি না (যাতে সিস্টেম ফাস্ট থাকে)। এর বদলে আমরা টেবিলের একটি নতুন কলাম ব্যবহার করি, যেমন `version` (ভার্সন)। 

**SQL Query Example:**
```sql
-- Step 1: সিটটি রিড করুন এবং বর্তমান ভার্সনটি জেনে নিন (কোনো লক ছাড়া)
SELECT is_booked, version 
FROM Seats 
WHERE seat_id = 101; 
-- ধরি, রেজাল্ট আসলো: is_booked = FALSE, version = 1

-- Step 2: আপডেট করার সময় কন্ডিশন দিন যে ভার্সনটি এখনও আগেরটিই আছে কিনা
UPDATE Seats 
SET is_booked = TRUE, 
    booked_by_user = 'User A', 
    version = version + 1   -- ভার্সন বাড়িয়ে দিন
WHERE seat_id = 101 
  AND version = 1;          -- মূল ট্রিক এখানেই!
```

**কীভাবে কাজ করে?**
*   ইউজার A এবং ইউজার B দুজনেই রিড করে দেখলো `version = 1`.
*   ইউজার A তার আপডেট রিকোয়েস্ট পাঠালো `WHERE version = 1` দিয়ে। আপডেট সফল হলো এবং ডাটাবেসে এখন `version = 2` হয়ে গেল।
*   এবার ইউজার B তার আপডেট রিকোয়েস্ট পাঠালো `WHERE version = 1` দিয়ে। কিন্তু ডাটাবেস চেক করে দেখবে বর্তমান ভার্সন ২। তাই ইউজার B এর আপডেট ফেল (Fail) করবে (Affected rows: 0 আসবে)। 
*   ব্যাকএন্ড কোড তখন ইউজার B কে একটি Error মেসেজ দেখাবে যে "সিটটি ইতোমধ্যে বুক হয়ে গেছে।"

**সুবিধা:** কোনো ডাটাবেস লক হয় না, তাই সিস্টেম অনেক ফাস্ট থাকে। 
**অসুবিধা:** ইউজারকে মাঝে মাঝে এরর মেসেজ দেখতে হয়।

---

### সমাধান ৩: Unique Constraint (ইউনিক কনস্ট্রেইন্ট) ব্যবহার করা

এটি অপটিমিস্টিক লকিং এর মতই আরেকটি বুদ্ধিমান উপায়, যেখানে আমরা ডাটাবেসের নিজস্ব ইউনিক কি (Unique Key) মেকানিজম ব্যবহার করি।

এর জন্য আমরা `Seats` টেবিল আপডেট না করে, নতুন একটি `Bookings` টেবিল ব্যবহার করতে পারি।

| booking_id | user_id | seat_id (UNIQUE) |
| :--- | :--- | :--- |

**কীভাবে কাজ করে?**
*   আমরা `seat_id` কলামটিকে `UNIQUE` কনস্ট্রেইন্ট দিয়ে রাখবো। অর্থাৎ একটি সিটের এন্ট্রি এই টেবিলে মাত্র একবারই থাকতে পারবে।
*   যখন ইউজার A এবং B সিটটি বুক করতে চাইবে, দুজনেই ইনসার্ট (Insert) করার চেষ্টা করবে:

**SQL Query Example:**
```sql
INSERT INTO Bookings (user_id, seat_id) VALUES ('User A', 101);
-- একই সাথে
INSERT INTO Bookings (user_id, seat_id) VALUES ('User B', 101);
```

*   ডাটাবেস ইঞ্জিনের নিজস্ব মেকানিজম অনুযায়ী, প্রথম যে ইনসার্ট রিকোয়েস্টটি পৌঁছাবে সেটি সফল হবে।
*   দ্বিতীয় রিকোয়েস্টটি পৌঁছালে ডাটাবেস সাথে সাথে একটি `Unique Constraint Violation Error` থ্রো করবে (কারণ 101 সিটটি ইতোমধ্যে ইনসার্ট হয়ে গেছে)। 
*   ব্যাকএন্ড কোডে এই এররটি ক্যাচ (Catch) করে ইউজার B কে বুকিং ফেইল মেসেজ দেখিয়ে দিতে হবে।

## ৫. ইন্টারভিউয়ের জন্য চূড়ান্ত টিপস: কখন কোনটি ব্যবহার করবেন?

ইন্টারভিউয়ার যদি প্রশ্ন করে, "তুমি কোন সলিউশনটি বেছে নেবে?" 
**উত্তর হবে:** এটি নির্ভর করে ইউজ কেস (Use Case) এর উপর।

1.  **Ticket Booking (টিকিট বুকিং):** যখন স্পাইডারম্যানের মতো হাইপড মুভির রিলিজ হয়, তখন একই সিটের জন্য প্রচুর কম্পিটিশন থাকে (High Collision Probability)। এই ক্ষেত্রে **Pessimistic Locking** (বা Redis এর মত In-memory লক) ব্যবহার করা ভালো, কারণ এতে ডাটা ইনকন্সিস্টেন্সি হওয়ার সুযোগই থাকে না।
2.  **E-commerce Product Update:** একটি প্রোডাক্টের দাম আপনি এবং আপনার কলিগ একই সাথে আপডেট করছেন, এমন হওয়ার সম্ভাবনা খুবই কম (Low Collision Probability)। এই ক্ষেত্রে **Optimistic Locking** বেস্ট। কারণ অকারণে লক করে সিস্টেম স্লো করার কোনো মানে হয় না।

এই ৩টি মেকানিজম খুব ভালোভাবে বুঝতে পারলে যেকোনো কনকারেন্সি সম্পর্কিত ডাটাবেস ডিজাইনের প্রশ্নের উত্তর সহজে দেওয়া সম্ভব।
