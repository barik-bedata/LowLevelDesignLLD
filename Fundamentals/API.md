# API (Application Programming Interface) এবং HTTP Fundamentals - বিস্তারিত গাইড

সফটওয়্যার ইঞ্জিনিয়ারিং ইন্টারভিউ, বিশেষ করে ট্রেইনি বা জুনিয়র লেভেলের জন্য, API এবং HTTP সম্পর্কিত বেসিকগুলো অত্যন্ত গুরুত্বপূর্ণ। MCQ থেকে শুরু করে টেকনিক্যাল ভাইভা - সব জায়গাতেই এই টপিকগুলো থেকে প্রশ্ন আসে। এই গাইডটি আপনাকে একদম শূন্য থেকে বিস্তারিত ধারণা দেবে।

---

## ১. API (এপিআই) কী? (What is an API?)

API এর পূর্ণরূপ হলো **Application Programming Interface**। সহজ ভাষায় বলতে গেলে, API হলো এমন একটি মাধ্যম যার সাহায্যে দুটি আলাদা সফটওয়্যার একে অপরের সাথে কথা বলতে বা ডাটা আদান-প্রদান করতে পারে। 

**বাস্তব জীবনের উদাহরণ:**
ধরুন, আপনি একটি রেস্টুরেন্টে খেতে গেছেন। 
*   **আপনি (Client):** আপনি মেনু দেখে ঠিক করলেন কী খাবেন। 
*   **রান্নাঘর (Server):** যেখানে খাবার তৈরি হয়। 
*   **ওয়েটার (API):** আপনি সরাসরি রান্নাঘরে গিয়ে খাবার আনতে পারেন না। আপনি ওয়েটারকে আপনার অর্ডার দেন। ওয়েটার আপনার অর্ডার রান্নাঘরে নিয়ে যায়, রান্নাঘর থেকে খাবার তৈরি হলে সেটা আবার আপনার টেবিলে এনে দেয়। 

এখানে ওয়েটার হলো API। সে আপনার (Client) রিকোয়েস্ট সার্ভারের (রান্নাঘর) কাছে নিয়ে যায় এবং সার্ভারের রেসপন্স (খাবার) আপনার কাছে ফিরিয়ে আনে।

**ডিজিটাল উদাহরণ:** 
যখন আপনি আপনার মোবাইলে আবহাওয়া দেখার অ্যাপ (Weather App) ওপেন করেন, তখন অ্যাপটি সরাসরি স্যাটেলাইটের সাথে কানেক্ট করে না। এটি আবহাওয়া দপ্তরের একটি সার্ভারে (যেমন AccuWeather) একটি API রিকোয়েস্ট পাঠায়। সার্ভার বর্তমান আবহাওয়ার ডাটা প্রসেস করে API-এর মাধ্যমে আপনার অ্যাপে পাঠিয়ে দেয়।

### API কেন ব্যবহার করা হয়?
১. **অ্যাবস্ট্রাকশন (Abstraction):** ভেতরের জটিল কোড লুকিয়ে রাখা যায়। যেমন, Google Maps API ব্যবহার করে আপনি সহজেই ম্যাপ দেখাতে পারেন, গুগল কীভাবে ম্যাপ রেন্ডার করছে তা আপনার জানার দরকার নেই।
২. **সিকিউরিটি (Security):** সার্ভারের সরাসরি অ্যাক্সেস না দিয়ে, শুধুমাত্র নির্দিষ্ট ডাটা API এর মাধ্যমে প্রদান করা যায়। 
৩. **রিইউজেবিলিটি (Reusability):** একবার একটি API বানালে, সেটি ওয়েবসাইট, মোবাইল অ্যাপ বা অন্য কোনো সিস্টেমে বারবার ব্যবহার করা যায়।

## ২. HTTP কী এবং কীভাবে কাজ করে? (HTTP Fundamentals)

**HTTP (HyperText Transfer Protocol)** হলো ইন্টারনেটে ডাটা (টেক্সট, ইমেজ, ভিডিও) আদান-প্রদান করার মূল প্রোটোকল বা নিয়মাবলি। যখনই আপনি ব্রাউজারে কোনো ওয়েবসাইটের ঠিকানা লেখেন, তখন ব্রাউজার সার্ভারকে একটি HTTP Request পাঠায়, এবং সার্ভার একটি HTTP Response ফেরত দেয়।

### Request-Response Cycle (রিকোয়েস্ট-রেসপন্স সাইকেল)
১. **Client (যেমন আপনার ব্রাউজার):** একটি নির্দিষ্ট URL-এ HTTP রিকোয়েস্ট পাঠায়। এই রিকোয়েস্টে একটি মেথড (যেমন GET বা POST), হেডার্স (Headers) এবং বডি (Body - যদি প্রয়োজন হয়) থাকে।
২. **Server:** রিকোয়েস্টটি গ্রহণ করে, ডাটাবেস চেক করে বা প্রয়োজনীয় লজিক প্রসেস করে।
৩. **Server Response:** সার্ভার প্রসেস শেষে ক্লায়েন্টকে একটি HTTP রেসপন্স পাঠায়। এই রেসপন্সে একটি স্ট্যাটাস কোড (যেমন 200 OK), হেডার্স এবং রেসপন্স বডি (যেমন HTML পেজ বা JSON ডাটা) থাকে।

### HTTP vs HTTPS
*   **HTTP:** ডাটা প্লেইন টেক্সট (Plain text) হিসেবে যায়। হ্যাকাররা সহজেই মাঝখান থেকে ডাটা পড়ে ফেলতে পারে (Man-in-the-middle attack)।
*   **HTTPS (HTTP Secure):** এখানে SSL/TLS এনক্রিপশন ব্যবহার করা হয়। ফলে ডাটা সিকিউরড বা এনক্রিপ্টেড অবস্থায় আদান-প্রদান হয়। ইন্টারভিউতে এটি একটি সাধারণ প্রশ্ন।

## ৩. HTTP Request Methods (Verbs) - বিস্তারিত

REST API তে বিভিন্ন ধরণের কাজের জন্য আলাদা আলাদা HTTP মেথড ব্যবহার করা হয়। এগুলোকে অনেক সময় CRUD (Create, Read, Update, Delete) অপারেশনের সাথে মেলানো হয়।

### ১. GET (ডাটা পড়ার জন্য)
*   **কাজ:** সার্ভার থেকে শুধুমাত্র ডাটা রিড বা রিট্রিভ করার জন্য ব্যবহার করা হয়।
*   **বৈশিষ্ট্য:** GET রিকোয়েস্ট দিয়ে সার্ভারের কোনো ডাটা পরিবর্তন, ডিলিট বা আপডেট করা উচিত নয়।
*   **URL-এ ডাটা:** GET রিকোয়েস্টে ডাটা URL-এর সাথে কোয়েরি প্যারামিটার হিসেবে যায় (যেমন: `example.com/api/users?name=john`)।
*   **লিমিটেশন:** যেহেতু ডাটা URL-এ যায়, তাই এর একটি সাইজ লিমিট থাকে।
*   **সিকিউরিটি:** পাসওয়ার্ড বা সেনসিটিভ ডাটা কখনো GET রিকোয়েস্টে পাঠানো উচিত নয়, কারণ এটি ব্রাউজার হিস্ট্রি এবং সার্ভার লগে সেভ হয়ে যায়।
*   **Idempotent:** হ্যাঁ, এটি Idempotent। (Idempotent কী তা নিচে বিস্তারিত আছে)।

### ২. POST (নতুন ডাটা তৈরি করার জন্য)
*   **কাজ:** সার্ভারে নতুন কোনো ডাটা (Resource) ক্রিয়েট করার জন্য ব্যবহার করা হয়।
*   **বৈশিষ্ট্য:** POST রিকোয়েস্টের মাধ্যমে পাঠানো ডাটা Request Body-তে থাকে, URL-এ নয়।
*   **সিকিউরিটি:** GET এর চেয়ে বেশি সিকিউরড, কারণ ডাটা বডিতে এনক্যাপসুলেটেড থাকে।
*   **Idempotent:** না, এটি Idempotent নয়। একই POST রিকোয়েস্ট বারবার পাঠালে সার্ভারে বারবার নতুন ডাটা তৈরি হবে।

### ৩. PUT (পুরো ডাটা আপডেট করার জন্য)
*   **কাজ:** সার্ভারে থাকা কোনো নির্দিষ্ট ডাটা আপডেট করার জন্য ব্যবহার করা হয়। যদি ডাটাটি না থাকে, তবে এটি নতুন করে তৈরিও করতে পারে ( নির্ভর করে লজিকের উপর)।
*   **বৈশিষ্ট্য:** PUT রিকোয়েস্ট পাঠানোর সময় আপনাকে পুরো ডাটা অবজেক্টটি পাঠাতে হবে। ধরুন একটি ইউজারের নাম এবং বয়স আছে। আপনি শুধু বয়স বদলাতে চান, তাও PUT ব্যবহার করলে আপনাকে নাম এবং বয়স দুটোই পাঠাতে হবে।
*   **Idempotent:** হ্যাঁ, এটি Idempotent। একই ডাটা দিয়ে বারবার PUT রিকোয়েস্ট পাঠালেও সার্ভারের ডাটা একই থাকবে।

### ৪. PATCH (আংশিক ডাটা আপডেট করার জন্য)
*   **কাজ:** সার্ভারের কোনো ডাটার আংশিক (Partial) পরিবর্তনের জন্য ব্যবহার করা হয়।
*   **বৈশিষ্ট্য:** উপরের উদাহরণ অনুযায়ী, শুধু বয়স বদলাতে চাইলে PATCH রিকোয়েস্টে শুধু বয়স পাঠালেই হবে, পুরো অবজেক্ট পাঠানোর দরকার নেই।
*   **Idempotent:** সাধারণত Idempotent নয়, তবে ইমপ্লিমেন্টেশনের উপর নির্ভর করে।

### ৫. DELETE (ডাটা মুছে ফেলার জন্য)
*   **কাজ:** সার্ভার থেকে নির্দিষ্ট ডাটা রিমুভ বা ডিলিট করার জন্য।
*   **Idempotent:** হ্যাঁ, এটি Idempotent। প্রথমবার ডিলিট করার পর ডাটা মুছে যাবে। এরপর একই রিকোয়েস্ট বারবার পাঠালেও ডাটা আর ডিলিট করার কিছু থাকবে না, তবে রেসপন্স একই রকম হতে পারে (যেমন 404 Not Found বা 200 OK)।

### ৬. OPTIONS (Preflight Request)
*   **কাজ:** ক্লায়েন্ট (যেমন ব্রাউজার) সার্ভারকে জিজ্ঞেস করে যে, নির্দিষ্ট কোনো API-তে কোন কোন মেথড (GET, POST ইত্যাদি) অ্যালাউড আছে এবং কোন অরিজিন থেকে রিকোয়েস্ট করা যাবে।
*   **CORS:** Cross-Origin Resource Sharing (CORS) এর ক্ষেত্রে ব্রাউজার আসল রিকোয়েস্ট পাঠানোর আগে স্বয়ংক্রিয়ভাবে একটি OPTIONS রিকোয়েস্ট পাঠায় (যাকে Preflight Request বলে) সিকিউরিটি চেক করার জন্য।

## ৪. Idempotency এবং Safe Methods (ইন্টারভিউয়ের জন্য খুব গুরুত্বপূর্ণ)

### Safe Methods কী?
যে HTTP মেথডগুলো সার্ভারের কোনো ডাটা পরিবর্তন (Modify) করে না, সেগুলোকে Safe Method বলে। এগুলো শুধুমাত্র Read-only অপারেশন।
*   **Safe Methods:** `GET`, `OPTIONS`, `HEAD`
*   **Unsafe Methods:** `POST`, `PUT`, `PATCH`, `DELETE`

### Idempotency (আইডেমপোটেন্সি) কী?
একটি অপারেশন Idempotent হওয়ার অর্থ হলো - সেই অপারেশনটি আপনি একবার করেন বা এক হাজার বার করেন, সার্ভারের ডাটার চূড়ান্ত অবস্থা (End result/state) একই থাকবে। 

**উদাহরণ দিয়ে বুঝি:**
*   **GET (Idempotent):** আপনি একটি ইউজারের ডাটা বারবার GET করলে ডাটা একই থাকবে, সার্ভারে কোনো চেঞ্জ হবে না।
*   **PUT (Idempotent):** আপনি যদি বলেন `Update user with ID 1 to name "Alice"`, আপনি এই কমান্ড ১০০ বার দিলেও ইউজারের নাম "Alice"-ই থাকবে।
*   **DELETE (Idempotent):** আপনি যদি বলেন `Delete user with ID 1`, প্রথমবার ইউজার ডিলিট হবে। পরের ৯৯ বার কমান্ড দিলে ডিলিট করার মতো ইউজার পাবে না, কিন্তু সার্ভারের আল্টিমেট স্টেট হলো "ইউজার 1 নেই" - যা সবক্ষেত্রেই সমান। 
*   **POST (Not Idempotent):** আপনি যদি `Create a user named "Alice"` কমান্ড ১০০ বার দেন, তবে সার্ভারে "Alice" নামের ১০০ টি নতুন ইউজার ক্রিয়েট হয়ে যাবে। প্রতিবার সার্ভারের স্টেট পরিবর্তন হচ্ছে। 

**সারসংক্ষেপ:**
| Method | Safe? | Idempotent? |
| :--- | :--- | :--- |
| GET | Yes | Yes |
| OPTIONS| Yes | Yes |
| HEAD | Yes | Yes |
| PUT | No | Yes |
| DELETE | No | Yes |
| POST | No | No |
| PATCH | No | Usually No |

## ৫. HTTP Status Codes (মেমোরাইজ করা জরুরি)

যখন আপনি API-তে রিকোয়েস্ট পাঠান, সার্ভার একটি ৩-ডিজিটের স্ট্যাটাস কোড দেয়, যা দিয়ে বোঝা যায় রিকোয়েস্টের কী অবস্থা। ইন্টারভিউ এবং MCQ এর জন্য এটি একদম মুখস্থ থাকা চাই। এগুলো ৫টি ক্লাসে বিভক্ত:

### 1xx : Informational (তথ্যমূলক)
রিকোয়েস্ট রিসিভ করা হয়েছে এবং প্রসেস চলছে।
*   `100 Continue`: সার্ভার রিকোয়েস্টের প্রাথমিক অংশ পেয়েছে, ক্লায়েন্ট এখন বাকি অংশ পাঠাতে পারে।

### 2xx : Success (সফলতা)
ক্লায়েন্টের রিকোয়েস্ট সার্ভার সফলভাবে গ্রহণ করেছে এবং প্রসেস করেছে।
*   **`200 OK`**: সবচেয়ে সাধারণ সাকসেস কোড। সাধারণত GET, PUT, PATCH রিকোয়েস্ট সফল হলে এটি দেওয়া হয়।
*   **`201 Created`**: POST রিকোয়েস্টের মাধ্যমে সার্ভারে নতুন কোনো ডাটা সফলভাবে তৈরি হলে এটি দেওয়া হয়।
*   **`202 Accepted`**: রিকোয়েস্ট প্রসেস করার জন্য গ্রহণ করা হয়েছে, কিন্তু প্রসেসিং এখনো শেষ হয়নি (Asynchronous processing এর ক্ষেত্রে)।
*   **`204 No Content`**: রিকোয়েস্ট সফল হয়েছে কিন্তু রেসপন্সে কোনো বডি বা ডাটা পাঠানোর নেই। সাধারণত DELETE সফল হলে এটি ব্যবহার করা হয়।

### 3xx : Redirection (রিডাইরেকশন)
রিকোয়েস্ট সম্পন্ন করতে ক্লায়েন্টকে অন্য কোনো URL-এ যেতে হবে।
*   **`301 Moved Permanently`**: যে URL-এ রিকোয়েস্ট করা হয়েছে, সেটি চিরস্থায়ীভাবে নতুন একটি URL-এ মুভ হয়ে গেছে। ব্রাউজার স্বয়ংক্রিয়ভাবে নতুন URL-এ চলে যায়। SEO এর জন্য এটি গুরুত্বপূর্ণ।
*   **`302 Found` (বা Temporarily Moved):** URL টি সাময়িকভাবে অন্য জায়গায় মুভ হয়েছে।
*   **`304 Not Modified`**: ক্লায়েন্টের কাছে আগে থেকেই যে ক্যাশ (Cache) করা ডাটা আছে, সার্ভারের ডাটা তার থেকে পরিবর্তন হয়নি। তাই সার্ভার নতুন করে ডাটা পাঠায় না, ক্লায়েন্ট তার ক্যাশ ব্যবহার করে। এটি পারফরম্যান্স বাড়ায়।
*   **`307 Temporary Redirect` & `308 Permanent Redirect`**: এগুলো 302 এবং 301 এর মতই কাজ করে, কিন্তু এরা রিডাইরেক্ট করার সময় HTTP মেথড পরিবর্তন করতে দেয় না (যেমন POST রিকোয়েস্ট রিডাইরেক্ট হয়ে POST-ই থাকবে)।

### 4xx : Client Error (ক্লায়েন্টের ভুল)
রিকোয়েস্টে কোনো ভুল আছে যা ক্লায়েন্টের (আপনার) দিক থেকে হয়েছে।
*   **`400 Bad Request`**: রিকোয়েস্টের সিনট্যাক্স ভুল, বা ডাটা ফরম্যাট ঠিক নেই। সার্ভার বুঝতে পারছে না।
*   **`401 Unauthorized`**: **(খুব ইম্পর্টেন্ট)** ক্লায়েন্ট কে, তা সার্ভার জানে না। অর্থাৎ ইউজার লগ-ইন করেনি বা সঠিক Authentication টোকেন দেয়নি। 
*   **`403 Forbidden`**: **(খুব ইম্পর্টেন্ট)** ক্লায়েন্ট কে, তা সার্ভার জানে (লগ-ইন করা আছে), কিন্তু এই নির্দিষ্ট কাজটি করার পারমিশন ক্লায়েন্টের নেই (Authorization issue)। *ইন্টারভিউতে 401 এবং 403 এর পার্থক্য খুব জিজ্ঞেস করে।*
*   **`404 Not Found`**: যে ডাটা বা URL খোঁজা হচ্ছে, তা সার্ভারে নেই।
*   **`405 Method Not Allowed`**: নির্দিষ্ট URL এর জন্য এই মেথড অ্যালাউড না। (যেমন ডাটা রিড করার API-তে কেউ POST রিকোয়েস্ট করলে)।
*   **`429 Too Many Requests`**: ক্লায়েন্ট নির্দিষ্ট সময়ে অতিরিক্ত বেশি রিকোয়েস্ট পাঠিয়ে ফেলেছে (Rate Limiting)।

### 5xx : Server Error (সার্ভারের ভুল)
সার্ভার কোনো কারণে রিকোয়েস্ট প্রসেস করতে ব্যর্থ হয়েছে। ক্লায়েন্টের রিকোয়েস্ট ঠিক ছিল।
*   **`500 Internal Server Error`**: সার্ভারের কোডে কোনো সমস্যা বা এক্সেপশন (Exception) দেখা দিয়েছে যা হ্যান্ডেল করা হয়নি। 
*   **`502 Bad Gateway`**: সার্ভার নিজে একটি প্রক্সি বা গেটওয়ে হিসেবে কাজ করছিল এবং পেছনের সার্ভার থেকে সে ইনভ্যালিড রেসপন্স পেয়েছে।
*   **`503 Service Unavailable`**: সার্ভার বর্তমানে ওভারলোডেড অথবা মেইনটেন্যান্স এর কারণে ডাউন আছে।
*   **`504 Gateway Timeout`**: প্রক্সি সার্ভার পেছনের সার্ভার থেকে সময়মতো কোনো রেসপন্স পায়নি (টাইমআউট হয়ে গেছে)।

## ৬. REST API আর্কিটেকচার (REST Constraints)

REST (Representational State Transfer) কোনো প্রোটোকল নয়, এটি API ডিজাইন করার একটি আর্কিটেকচারাল স্টাইল বা কিছু গাইডলাইন। একটি API-কে পুরোপুরি 'RESTful' হতে হলে ৬টি নিয়ম (Constraints) মানতে হয়:

১. **Client-Server Architecture:** ক্লায়েন্ট (UI/ব্রাউজার) এবং সার্ভার (ডাটাবেস/লজিক) সম্পূর্ণ আলাদা হতে হবে। এরা একে অপরের উপর নির্ভরশীল হবে না।
২. **Statelessness (স্টেটলেসনেস - ভেরি ইম্পর্টেন্ট):** সার্ভার ক্লায়েন্টের কোনো সেশন বা স্টেট (অবস্থা) মনে রাখবে না। প্রতিটি রিকোয়েস্ট সম্পূর্ণ স্বাধীন হতে হবে। রিকোয়েস্ট প্রসেস করার জন্য প্রয়োজনীয় সব তথ্য ওই রিকোয়েস্টের ভেতরেই থাকতে হবে (যেমন প্রতি রিকোয়েস্টের সাথে Auth Token পাঠানো)।
৩. **Cacheability (ক্যাশেবিলিটি):** রেসপন্সের ডাটা ক্যাশে (Cache) করে রাখা যাবে কি না, তা রেসপন্সে বলে দিতে হবে (Cache-Control Header এর মাধ্যমে), যাতে পারফরম্যান্স বাড়ে।
৪. **Layered System:** ক্লায়েন্ট এবং সার্ভারের মাঝখানে একাধিক লেয়ার থাকতে পারে (যেমন লোড ব্যালেন্সার, প্রক্সি, ফায়ারওয়াল)। ক্লায়েন্ট জানবে না সে সরাসরি মেইন সার্ভারের সাথে কানেক্টেড নাকি অন্য কোনো লেয়ারের সাথে।
৫. **Uniform Interface:** API এর ইউআরএল এবং ডাটা স্ট্রাকচার কনসিস্টেন্ট হতে হবে। (যেমন সব ইউজার পেতে `/users`, নির্দিষ্ট ইউজার পেতে `/users/123`)।
৬. **Code on Demand (Optional):** সার্ভার চাইলে ক্লায়েন্টকে এক্সিকিউটেবল কোড (যেমন জাভাস্ক্রিপ্ট) পাঠাতে পারে যা ক্লায়েন্ট সাইডে রান করবে। এটি ঐচ্ছিক নিয়ম।

### Richardson Maturity Model (REST এর লেভেল)
API কতটা RESTful তার উপর ভিত্তি করে ৪টি লেভেল আছে:
*   **Level 0 (Swamp of POX):** শুধু একটি URL এবং একটি মেথড (সাধারণত POST) ব্যবহার করে সব কাজ করা (যেমন SOAP)।
*   **Level 1 (Resources):** আলাদা আলাদা ডাটার জন্য আলাদা URL ব্যবহার করা (যেমন `/users`, `/products`)।
*   **Level 2 (HTTP Verbs):** URL এর পাশাপাশি সঠিক HTTP মেথড (GET, POST, PUT, DELETE) ব্যবহার করা এবং সঠিক স্ট্যাটাস কোড দেওয়া। বেশিরভাগ আধুনিক API এই লেভেলে থাকে।
*   **Level 3 (Hypermedia/HATEOAS):** HATEOAS (Hypermedia As The Engine Of Application State)। এর মানে হলো API রেসপন্সের সাথে সাথে সেই ডাটার সাথে পরবর্তীতে আর কী কী কাজ করা যাবে, তার লিংকও দিয়ে দেওয়া।

## ৭. API Security & Authentication (কিভাবে API সিকিউর করা হয়?)

যেহেতু API ইন্টারনেট দিয়ে অ্যাক্সেস করা যায়, তাই যে কেউ যেন ডাটা না দেখতে পারে তার জন্য সিকিউরিটি দরকার।

১. **Basic Authentication:** ইউজারের ইমেইল এবং পাসওয়ার্ড Base64 এ এনকোড করে হেডার্সে পাঠানো হয়। এটি একেবারেই সিকিউর না (যদি না HTTPS ব্যবহার করা হয়)।
২. **Session-based Authentication (Cookies):** ইউজার লগইন করলে সার্ভার ডাটাবেসে একটি সেশন তৈরি করে এবং ব্রাউজারকে একটি Session ID কুকি হিসেবে দিয়ে দেয়। পরের রিকোয়েস্টগুলোতে ব্রাউজার কুকি পাঠায়। এটি REST এর Statelessness নীতির কিছুটা পরিপন্থী।
৩. **Token-based Authentication (JWT):** আধুনিক API তে এটি সবচেয়ে বেশি ব্যবহৃত হয়। 
    *   **JWT (JSON Web Token) কী?** এটি একটি এনক্রিপ্টেড স্ট্রিং। ইউজার লগইন করলে সার্ভার একটি JWT তৈরি করে দেয়। এর ৩টি অংশ থাকে: Header, Payload (ডাটা যেমন ইউজারের আইডি) এবং Signature।
    *   **কিভাবে কাজ করে?** ক্লায়েন্ট টোকেনটি সেভ করে রাখে (সাধারণত Local Storage বা HttpOnly Cookie তে)। এরপর প্রতিটি API রিকোয়েস্টের `Authorization` হেডারে (Bearer Token হিসেবে) এই টোকেনটি পাঠায়। সার্ভার টোকেনের সিগনেচার ভেরিফাই করে বোঝে যে ইউজার ভ্যালিড। এতে সার্ভারকে ডাটাবেসে সেশন সেভ রাখতে হয় না (Stateless)।
৪. **OAuth 2.0:** যখন আপনি অন্য কোনো থার্ড-পার্টি অ্যাপকে আপনার গুগল বা ফেসবুক অ্যাকাউন্টের অ্যাক্সেস দেন (যেমন "Login with Google"), তখন OAuth 2.0 ব্যবহৃত হয়। এটি মূলত Authorization ফ্রেমওয়ার্ক।

## ৮. CORS (Cross-Origin Resource Sharing)

ইন্টারভিউতে CORS নিয়ে প্রায়ই প্রশ্ন আসে। 
*   **Same-Origin Policy:** ব্রাউজারের একটি সিকিউরিটি মেকানিজম আছে। এটি একটি ওয়েবসাইটকে (যেমন `frontend.com`) অন্য একটি ওয়েবসাইটের (যেমন `api.backend.com`) ডাটা সরাসরি অ্যাক্সেস করতে বাধা দেয়। ডোমেইন, পোর্ট বা প্রোটোকল (http/https) আলাদা হলেই তাকে Cross-Origin বলা হয়।
*   **CORS কী?** CORS হলো এমন একটি মেকানিজম যার মাধ্যমে ব্যাকএন্ড সার্ভার ব্রাউজারকে বলে দেয় যে, "হ্যাঁ, তুমি `frontend.com` থেকে আমার কাছে রিকোয়েস্ট পাঠাতে পারো, আমি তাকে অ্যালাউ করছি।"
*   **CORS Error কেন হয়?** যদি ব্যাকএন্ড সার্ভার তার রেসপন্স হেডারে `Access-Control-Allow-Origin: *` (বা নির্দিষ্ট ডোমেইন) সেট না করে দেয়, তবে ব্রাউজার সিকিউরিটি পারপাসে সেই ডাটা আটকে দেয় এবং কনসোলে CORS error দেখায়। মনে রাখবেন, রিকোয়েস্ট সার্ভারে ঠিকই যায়, কিন্তু ব্রাউজার রেসপন্সটি আপনার জাভাস্ক্রিপ্ট কোডকে পড়তে দেয় না।
*   **Preflight Request:** ব্রাউজার আসল POST বা PUT রিকোয়েস্ট পাঠানোর আগে একটি `OPTIONS` রিকোয়েস্ট পাঠিয়ে চেক করে নেয় সার্ভার CORS অ্যালাউ করছে কিনা।

## ৯. অন্যান্য গুরুত্বপূর্ণ কনসেপ্ট

### Rate Limiting & Throttling
*   কেউ যাতে ইচ্ছাকৃতভাবে বা ভুল করে বারবার রিকোয়েস্ট পাঠিয়ে আপনার সার্ভার ডাউন করে না দিতে পারে (DDoS Attack), তার জন্য Rate Limiting ব্যবহার করা হয়।
*   যেমন, "একজন ইউজার মিনিটে সর্বোচ্চ ১০০টি রিকোয়েস্ট করতে পারবে।" লিমিট ক্রস করলে সার্ভার `429 Too Many Requests` স্ট্যাটাস কোড দিবে।
*   অ্যালগরিদম: Token Bucket, Leaky Bucket ইত্যাদি।

### API Pagination, Filtering & Sorting
*   যখন ডাটাবেসে লাখ লাখ ডাটা থাকে, তখন একটি GET রিকোয়েস্টে সব ডাটা পাঠানো বোকামি। তাই API তে Pagination ব্যবহার করা হয় (যেমন `?page=1&limit=20`)।

### REST vs GraphQL
*   **REST:** নির্দিষ্ট ডাটার জন্য নির্দিষ্ট এন্ডপয়েন্ট (URL) থাকে। অনেক সময় প্রয়োজনের চেয়ে বেশি ডাটা (Over-fetching) বা কম ডাটা (Under-fetching) চলে আসে। 
*   **GraphQL:** এন্ডপয়েন্ট একটাই থাকে (সাধারণত `/graphql`)। ক্লায়েন্ট তার ঠিক যে যে ফিল্ডের ডাটা দরকার, শুধু সেগুলোই চেয়ে কোয়েরি করতে পারে। এতে Over-fetching/Under-fetching এর সমস্যা দূর হয়।

## ১০. সাধারণ MCQ এবং ইন্টারভিউ প্রশ্নাবলি

১. **প্রশ্ন:** একটি রিসোর্স ডিলিট করার পর রেসপন্স হিসেবে বডিতে কোন ডাটা পাঠানোর দরকার না হলে কোন স্ট্যাটাস কোড দেওয়া উচিত?
   **উত্তর:** 204 No Content.

২. **প্রশ্ন:** 401 Unauthorized এবং 403 Forbidden এর মূল পার্থক্য কী?
   **উত্তর:** 401 মানে সার্ভার জানে না আপনি কে (Authentication ফেল করেছে)। 403 মানে সার্ভার জানে আপনি কে, কিন্তু আপনার ওই কাজটি করার অধিকার নেই (Authorization ফেল করেছে)।

৩. **প্রশ্ন:** REST API এ Idempotent মেথড কোনগুলো?
   **উত্তর:** GET, PUT, DELETE, OPTIONS, HEAD.

৪. **প্রশ্ন:** আপনি একটি ই-কমার্স সাইটে শপিং কার্টে নতুন একটি আইটেম অ্যাড করতে চান। কোন HTTP মেথড ব্যবহার করবেন?
   **উত্তর:** POST.

৫. **প্রশ্ন:** সার্ভারে কোনো সমস্যা হলে, ক্লায়েন্ট কোন সিরিজের স্ট্যাটাস কোড পাবে?
   **উত্তর:** 5xx (যেমন 500 Internal Server Error)।

৬. **প্রশ্ন:** CORS Error কে দেয়? সার্ভার নাকি ব্রাউজার?
   **উত্তর:** ব্রাউজার। সার্ভার ডাটা পাঠায়, কিন্তু সার্ভারের হেডারে সঠিক CORS পলিসি না থাকলে ব্রাউজার সেটি ব্লক করে দেয়।

৭. **প্রশ্ন:** JWT টোকেনের কয়টি অংশ থাকে এবং কী কী?
   **উত্তর:** ৩টি অংশ: Header, Payload, Signature.

এই ডকুমেন্টটি মনোযোগ দিয়ে পড়লে API এবং HTTP সংক্রান্ত প্রায় যেকোনো এমসিকিউ বা বেসিক ইন্টারভিউ প্রশ্নের উত্তর আপনি খুব সহজেই দিতে পারবেন। শুভকামনা!
