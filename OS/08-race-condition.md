# Race Condition (রেস কন্ডিশন)

অপারেটিং সিস্টেম এবং মাল্টিথ্রেডিং (Multithreading) এর জগতে **Race Condition** খুবই কমন এবং মারাত্মক একটি বাগ (Bug)।

## ১. Race Condition কী?
যখন একাধিক প্রসেস বা থ্রেড একই সাথে (Concurrently) কোনো একটি শেয়ার করা ডাটা বা মেমোরি অ্যাক্সেস করে এবং ডাটাটি পরিবর্তন (Modify) করার চেষ্টা করে, তখন রেস কন্ডিশন তৈরি হয়। 
কোন থ্রেডটি আগে কাজ শেষ করবে তার কোনো নিশ্চয়তা থাকে না (এটি CPU শিডিউলিং এর উপর নির্ভর করে)। থ্রেডগুলোর এই 'প্রতিযোগিতা' বা 'রেস' এর কারণে শেয়ার করা ডাটাটির চূড়ান্ত ফলাফল ভুল বা অপ্রত্যাশিত (Unexpected) আসতে পারে। এই অবস্থাকেই Race Condition বলে।

**সহজ কথায়:** যখন আউটপুট নির্ভর করে কোন থ্রেড কখন এক্সিকিউট হচ্ছে (Timing/Execution order) তার উপর, তখন তাকে Race Condition বলে।

## ২. রেস কন্ডিশনের ৩টি বাস্তব জীবনের উদাহরণ (Real-world Examples)

### উদাহরণ ১: জয়েন্ট ব্যাংক অ্যাকাউন্ট (Joint Bank Account)
স্বামী এবং স্ত্রীর একটি জয়েন্ট ব্যাংক অ্যাকাউন্ট আছে, যেখানে ব্যালেন্স আছে ১০,০০০ টাকা।
*   স্বামী ATM বুথ থেকে ৫,০০০ টাকা তোলার চেষ্টা করছে।
*   ঠিক একই সেকেন্ডে স্ত্রী তার মোবাইল অ্যাপ থেকে ৫,০০০ টাকা অন্য অ্যাকাউন্টে ট্রান্সফার করার চেষ্টা করছে।

**সমস্যা কীভাবে হবে?**
1. স্বামীর থ্রেড (T1) ব্যালেন্স চেক করলো: ১০,০০০ টাকা।
2. স্ত্রীর থ্রেড (T2) ব্যালেন্স চেক করলো: ১০,০০০ টাকা।
3. T1 ব্যালেন্স থেকে ৫,০০০ টাকা কাটলো (নতুন ব্যালেন্স ১০,০০০ - ৫,০০০ = ৫,০০০) এবং ডাটাবেসে সেভ করলো।
4. T2 তার মেমোরিতে থাকা ১০,০০০ টাকা থেকে ৫,০০০ টাকা কাটলো (কারণ সে আগেই ব্যালেন্স ১০,০০০ দেখে নিয়েছিল) এবং নতুন ব্যালেন্স ৫,০০০ হিসেবে ডাটাবেসে আপডেট করে দিলো (আগের আপডেটটিকে ওভাররাইট করে)।
**ফলাফল:** অ্যাকাউন্ট থেকে মোট ১০,০০০ টাকা বের হয়ে গেছে, কিন্তু ডাটাবেস দেখাচ্ছে অ্যাকাউন্টে এখনো ৫,০০০ টাকা আছে! এটি একটি ব্যাংকের জন্য বিশাল ক্ষতি।

**টাইমলাইন চিত্র (Timeline Diagram):**
| Time | Husband (ATM - T1) | Wife (App - T2) | Bank Database (Balance) |
| :--- | :--- | :--- | :--- |
| T1 | `Read Balance` (দেখেছে ১০,০০০) | | **১০,০০০** |
| T2 | | `Read Balance` (দেখেছে ১০,০০০) | **১০,০০০** |
| T3 | `Calculate: 10k - 5k = 5k` | `Calculate: 10k - 5k = 5k` | **১০,০০০** |
| T4 | `Write Balance (5k)` | | **৫,০০০** |
| T5 | | `Write Balance (5k)` | **৫,০০০** *(ভুল! 0 হওয়ার কথা)* |

### উদাহরণ ২: সিনেমা বা ট্রেনের টিকিট বুকিং (Ticket Booking System)
আপনি এবং অন্য একজন ব্যক্তি একই সময়ে অনলাইনে একটি মুভির শেষ টিকিটটি কাটার চেষ্টা করছেন। 
বর্তমানে সিস্টেমে Available Ticket = 1.

**সমস্যা কীভাবে হবে?**
1. আপনার থ্রেড চেক করলো Available Ticket > 0 কি না। হ্যাঁ (1 আছে)।
2. অপর ব্যক্তির থ্রেডও চেক করলো Available Ticket > 0 কি না। হ্যাঁ (1 আছে)।
3. আপনার থ্রেড আপনার জন্য টিকিট বুক করলো এবং Available Ticket 0 করে দিলো।
4. অপর ব্যক্তির থ্রেডও তার জন্য টিকিট বুক করলো এবং Available Ticket 0 করে দিলো (বা -1 হয়ে গেলো)।
**ফলাফল:** ১টি টিকিটের বিপরীতে ২ জনের নামে বুকিং হয়ে গেছে! হলে গিয়ে দেখবেন ২ জন একই সিটে বসতে চাচ্ছে।

**টাইমলাইন চিত্র (Timeline Diagram):**
| Time | You (Thread A) | Other Person (Thread B) | Booking System (Tickets) |
| :--- | :--- | :--- | :--- |
| T1 | `Check Ticket` (পেয়েছে 1) | | **1** |
| T2 | | `Check Ticket` (পেয়েছে 1) | **1** |
| T3 | `Book Ticket` (আপডেট টু 0) | | **0** *(সিট আপনার)* |
| T4 | | `Book Ticket` (আপডেট টু -1) | **-1** *(ক্র্যাশ! ডাবল বুকিং)* |

### উদাহরণ ৩: ই-কমার্স ইনভেন্টরি বা লাইক কাউন্টার (Like Counter on Facebook)
ফেসবুকে একটি পোস্টে বর্তমানে 100 টি লাইক আছে। ২ জন মানুষ ঠিক একই মুহূর্তে লাইক বাটনে ক্লিক করলো।

**সমস্যা কীভাবে হবে?**
`Like = Like + 1` এই কাজটি আসলে ৩ ধাপে হয়: (১) Read Like, (২) Increment 1, (৩) Write Like.
1. Thread A ডাটাবেস থেকে বর্তমান লাইক পড়লো: 100.
2. Thread B ডাটাবেস থেকে বর্তমান লাইক পড়লো: 100.
3. Thread A এক বাড়ালো (101) এবং ডাটাবেসে লিখলো।
4. Thread B তার পড়া 100 কে এক বাড়ালো (101) এবং ডাটাবেসে লিখলো।
**ফলাফল:** ২ জন মানুষ লাইক দেওয়ার পর লাইক 102 হওয়ার কথা ছিল, কিন্তু ডাটাবেসে সেভ হলো 101। একটি লাইক বাতাসে হারিয়ে গেল।

## ৩. সমাধান কী? (How to prevent Race Condition?)
রেস কন্ডিশন এড়ানোর প্রধান উপায় হলো **Mutual Exclusion (পারস্পরিক বর্জন)** নিশ্চিত করা। এর মানে হলো, যখন একটি থ্রেড শেয়ার করা ডাটা নিয়ে কাজ করছে, তখন অন্য কোনো থ্রেড সেখানে ঢুকতে পারবে না। 
OS এ এর জন্য কিছু মেকানিজম ব্যবহার করা হয়:
*   **Locks / Mutex (Mutually Exclusive):** ডাটাবেস বা শেয়ার্ড মেমোরিতে ঢোকার আগে থ্রেড একটি চাবি (Lock) নিয়ে নেয়। কাজ শেষ করে চাবি ফেরত দেয়। চাবি না পাওয়া পর্যন্ত অন্য থ্রেডগুলোকে অপেক্ষা করতে হয়।
*   **Semaphores (সেমাফোর):** সিগন্যালিং মেকানিজম যার মাধ্যমে থ্রেডগুলোর প্রবেশ নিয়ন্ত্রণ করা হয়।
